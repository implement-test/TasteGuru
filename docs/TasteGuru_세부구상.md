## 1. 개발 전 확인 필요 분석

### 1-1. 쿠팡, 컬리 등 온라인 마켓에서 정보 가져오기 → **일부 가능**

| 출처 | 방법 | 결과 | 가져올 수 있는 정보 | 비고 |
| --- | --- | --- | --- | --- |
| 네이버 쇼핑 | 공식 **검색 API** (`/v1/search/shop.json`) | **가능** | 제품명, 대표 이미지, 최저가·최고가, 판매처, 브랜드·제조사, 카테고리 1~4 | 무료, 하루 25,000회. 키는 서버에만 둠. 네이버 쇼핑에 쿠팡·컬리 상품도 상당수 노출되므로 실질적으로 **가장 넓은 입력 경로** |
| 쿠팡 | 파트너스 **상품 검색 API** | 조건부 | 상품명, 이미지, 가격, 링크 | 파트너스 가입 후 **최종 승인(누적 판매 실적 조건, 블로그 기준 15만 원)** 이후에만 키 발급. 본인 구매로 실적 쌓기 금지. 개인 취미 프로젝트에는 현실성이 낮음 |
| 쿠팡 | 상품 페이지 직접 크롤링 | **불가에 가까움** | — | 서버 요청이 봇 차단(Access Denied)되는 사례 다수, 약관상 자동 수집 제한. 유지보수 부담 큼 |
| 컬리 | 공식 API | **없음** | — | 웹이 내부적으로 쓰는 비공식 경로만 존재 → 구조 변경 시 바로 깨짐. 로그인·배송지 기반 정보는 비로그인 조회 불가 |
| 공통 | 상품 URL의 **Open Graph 메타**(`og:title`, `og:image`) 읽기 | 일부 가능 | 제목, 대표 이미지 | 사이트별로 봇 차단·JS 렌더링 때문에 실패할 수 있음. 실패하면 직접 입력으로 자연스럽게 넘어가게 설계 |
| 공통 | 영양 정보 추출 | **불가** | — | 영양성분표는 대부분 **상세페이지 이미지 안**에 있어 텍스트로 가져올 수 없음 (이미지 판독은 AI 분석에 해당해 `하지 않을 것`과 충돌) |

**결론과 추천 입력 흐름**

1. **제품 검색(기본)**: 앱 안에서 제품명을 치면 네이버 쇼핑 검색 결과가 뜨고, 고르면 이름·이미지·브랜드·가격·카테고리가 자동 입력됨
2. **URL 붙여넣기(보조)**: 쿠팡·컬리 링크를 붙여넣으면 서버가 OG 메타 추출을 시도 → 실패 시 "직접 입력해 주세요" 안내
3. **직접 입력 + 사진 촬영/업로드**: 항상 가능한 마지막 경로. 모바일에서는 카메라 바로 열기

> ⚠️ 이 세션의 네트워크 정책상 쿠팡·컬리·네이버에 직접 접속 테스트를 하지 못했습니다. 위 판단은 공개 자료 기준이며, **개발 0단계에서 실제 호출 PoC로 재확인**합니다.

**이미지 저작권 메모**: 쇼핑몰 이미지는 판매자 저작물입니다. 10인 이하 비공개 그룹이라 위험은 낮지만, 기본은 **원본 이미지 URL만 저장(핫링크)** 하고, 사용자가 직접 찍은 사진만 우리 저장소에 올리는 방식을 추천합니다. 링크가 깨지면 기본 일러스트로 대체합니다.

### 1-2. (추가) 영양 정보 자동 입력 → **일부 가능**

- 식약처 **식품영양성분 DB(K-FIND, 2026-07 출범)** 를 공공데이터포털 Open API로 조회 가능 (가공식품 약 29.8만 건)
- 쇼핑몰 제품명 ≠ DB 제품명인 경우가 많아 자동 매칭은 불확실 → "영양 정보 찾기" 버튼으로 사용자가 직접 선택
- **MVP 이후**로 미루는 것을 추천 (명세의 핵심 목적은 맛 평가)

### 1-3. (추가) 상시 운영 → **가능**

- 이미 쓰고 있는 **Cloudflare Workers Paid** 포함량 안에서 운영 → 추가 비용 없음, Supabase 무료 플랜의 7일 비활성 일시정지 문제 없음
- D1 Time Travel로 최근 30일 아무 시점으로 복구 가능

### 1-4. (추가) Supabase 대신 Cloudflare만으로 개발 → **가능**

- DB = D1, 사진 = R2, 로그인 = Better Auth(Google), 호스팅 = Workers Static Assets, 예약 작업 = Cron Triggers
- 현재 사용량(10/1~10/11)은 월 포함량 대비 요청 약 1%, CPU 약 6%, R2 저장 약 40% → TasteGuru 추가 후에도 포함량 안
- 자세한 분석은 `TasteGuru_Cloudflare_분석.md`

## 3. 기술 스택 추천 (Cloudflare 단독)

| 구분 | 추천 | 이유 |
| --- | --- | --- |
| 화면 | **React + Vite (SPA) + TypeScript** | 지인 전용이라 검색 노출(SSR) 불필요. 빌드된 화면 파일은 정적 자산으로 제공되어 Worker CPU를 거의 쓰지 않음. 같은 계정의 sf6-repository(Next.js/OpenNext)가 요청당 CPU 약 60 ms·캐시 4GB로 무거운 것과 대비 |
| API | **Hono** | Workers 전용 경량 프레임워크. 네이버 API 키 숨기기·URL 메타 추출 등 **서버 작업**을 처리(브라우저에서는 CORS로 막힘) |
| DB | **Cloudflare D1 + Drizzle ORM** | 평가·태그·묶음은 다대다 관계와 **평균 집계**가 핵심 → 관계형(SQL) DB가 적합. Drizzle로 타입 안전한 쿼리·마이그레이션. 위치는 **apac** 지정 |
| 인증 | **Better Auth – Google 로그인** + 초대 링크 | D1에 세션·계정 저장, Workers에서 동작. 초대 토큰 검증 후에만 가입 허용 |
| 권한 | API 코드에서 검사 | 메모 전체 공개로 규칙 단순: 읽기 = 그룹원 전체, 수정·삭제 = 본인 또는 관리자 |
| 파일 저장 | **Cloudflare R2** | 업로드 전 브라우저에서 WebP로 리사이즈·압축(장당 약 300 KB). 전송 요금 없음 |
| 호스팅 | **Workers + Static Assets** | 화면 + API를 Worker 하나로 배포. `wrangler deploy` 또는 GitHub 연동 자동 배포 |
| 예약 작업·백업 | **Cron Triggers + D1 Time Travel** | 주 1회 JSON 백업을 R2에 저장, 30일 시점 복구 |
| UI | **shadcn/ui + Tailwind CSS** | 컴포넌트 코드를 프로젝트에 복사해 쓰는 방식이라 **파스텔·레트로 테마로 자유롭게 변형** 가능. Radix 기반이라 키보드·스크린리더 접근성 기본 제공. 다크 모드 내장 |
| 차트 | **Recharts** | 맛 프로필 레이더 차트, 묶음 비교 겹쳐 보기 |

**검토했지만 제외한 것**

- Supabase + Vercel: 기능상 문제는 없지만 이미 Cloudflare 유료 플랜을 쓰고 있어 서비스·키 관리가 늘고, 무료 플랜 일시정지·백업 부재 문제가 있음
- Next.js on Cloudflare(OpenNext): 동작은 하지만 이 규모에 비해 CPU·캐시 저장 부담이 큼
- Firebase: NoSQL이라 "항목별 평균", "묶음-음식 다대다" 같은 집계·관계 처리가 번거로움

## 4. 데이터 모델 (초안, D1/SQLite)

```
user / session / account / verification   Better Auth 기본 테이블 (구글 계정, 세션)
profiles          사용자 추가 정보 (user_id, 닉네임, role: admin|member, 가입일)
invites           초대 링크 (token, 만든 사람, 만료일, 사용한 사람, 사용일) — 1회용

foods             음식 (이름, 종류: product|meal_kit|delivery, 브랜드, 가게명(배달), 가격,
                       원본 URL, 입력 출처: naver|url|manual, 등록자, 등록일)
food_images       사진 (food_id, 외부 이미지 URL 또는 R2 키, 순서) — 음식당 최대 5
tags              태그 (이름, 색상, 만든 사람)
food_tags         음식-태그 (다대다)

taste_attributes  맛 항목 (이름, 아이콘, 강도 설명, 순서, 활성 여부) — 관리자가 관리
ratings           평가 (food_id, user_id, 종합 점수 1~5, 메모(전체 공개), 수정일)  ※ (food_id, user_id) 유일
rating_scores     맛 강도 (rating_id, attribute_id, 0~5) — 매긴 항목만 행이 생김

comparisons       묶음 비교 (제목, 설명, 만든 사람)
comparison_items  묶음-음식 (comparison_id, food_id, 순서)

[뷰] food_stats   음식별 종합 평균, 맛 항목별 평균 강도, 평가 인원 수
```

**핵심 설계 포인트**

- **묶음 비교는 음식을 "참조"만 함** → 묶음에서 점수를 고치면 같은 `ratings` 행을 고치는 것이므로 개별 점수도 자동으로 바뀜 (명세 요구사항이 구조적으로 보장됨)
- **일부 항목만 평가**: 매긴 항목만 `rating_scores`에 저장 → 평균 계산 시 **안 매긴 사람은 그 항목 평균에서 제외**(0점 취급 안 함)
- **덮어쓰기**: `(food_id, user_id)` 유일 제약 + upsert. 다시 평가하면 기존 맛 강도 행은 지우고 새로 저장
- **사진 5장 제한**: API에서 업로드 전 개수 확인 (DB 트리거 대신 코드에서 검사)
- 그룹이 1개라 그룹 테이블 없음

## 5. 화면 구성 (정보 구조)

```
로그인 ─ 초대 확인
│
├─ 홈 (음식 목록)
│   ├─ 검색 · 태그 필터 · 정렬(평균 높은순 / 최근 / 내가 안 먹어본 것)
│   └─ 카드: 대표 사진, 이름, 종합 평균 ★, 맛 프로필 미니 아이콘
│
├─ 음식 추가 ── 종류 선택(완제품/밀키트/배달 메뉴) → [제품 검색] [URL 붙여넣기] [직접 입력]
│                └─ 저장 직후 "바로 평가하기"로 이어짐
│
├─ 음식 상세
│   ├─ 사진(최대 5) · 기본 정보 · 태그
│   ├─ 그룹 평균 맛 프로필(레이더) + 내 프로필 겹쳐 보기
│   ├─ 내 평가 (종합 ★ + 맛 강도 0~5, 건너뛰기 가능 + 메모)
│   └─ 그룹원별 평가 목록 (종합 점수·맛 강도·메모)
│
├─ 묶음 비교
│   ├─ 목록 (예: "고기 만두 비교")
│   └─ 상세: 비교 표(셀에서 내 점수 수정) ↔ 레이더 겹쳐 보기 · 기존 음식 추가 / 새 음식 추가
│
├─ 내 평가 모아보기
├─ 태그 관리
├─ 설정: 글자 크기(4단계) · 테마(라이트/다크/시스템) · 데이터 내보내기(CSV·JSON)
├─ 업데이트 내역  ← 기본 포함
└─ 관리자: 초대 링크 발급, 멤버 관리, 맛 항목 관리

초대 링크로 접속 → 구글 로그인 → 닉네임 입력 → 가입 완료
```

- 모바일: 하단 탭바(홈 / 추가 / 비교 / 내 평가 / 설정), PC·태블릿: 좌측 사이드바
- 평가 입력은 **한 손 조작**을 우선: 항목별 큰 버튼(0~5) 또는 슬라이더, 미평가 상태가 기본

## 6. 디자인 방향

| 키워드 | 표현 방법 |
| --- | --- |
| 파스텔 | 배경·카드 채움에 파스텔(복숭아·민트·라벤더·버터 옐로). **글자에는 파스텔을 쓰지 않음**(대비 부족) |
| 귀여움 | 큰 둥근 모서리, 맛 항목별 아이콘(🌶️ 매운맛, 🍬 단맛, 🧂 짠맛 …), 빈 화면 일러스트 |
| 레트로 | 제목에 픽셀 느낌 한글 폰트(예: 갈무리 – OFL 무료), 굵은 외곽선 + 살짝 어긋난 그림자, 체크무늬·도트 배경 포인트 |

- **라이트/다크**: 색을 CSS 변수(토큰)로 정의하고 다크 모드에서는 채도를 낮춘 파스텔 + 짙은 남색 배경
- **접근성**
  - 글자 크기: 설정에서 4단계(작게/보통/크게/아주 크게) → 루트 글자 크기를 바꾸고 모든 크기를 `rem`으로 지정
  - 대비: 본문 글자 WCAG AA(4.5:1) 이상, 색만으로 정보 전달 금지(점수는 숫자 병기)
  - 키보드 조작·포커스 표시, 터치 영역 44px 이상
- 본문 폰트는 가독성 좋은 Pretendard, 픽셀 폰트는 제목·로고에만

## 7. 백업/내보내기 → **수동 내보내기(CSV·JSON) + D1 Time Travel(30일) + 주 1회 자동 백업(R2)**

- **D1 Time Travel**: Workers Paid는 최근 30일 아무 시점(분 단위)으로 복구 가능, 추가 비용 없음 → 실수로 지운 데이터 복구용
- **주간 자동 백업**: Cron Trigger가 매주 전체 데이터를 JSON으로 만들어 R2의 `backups/` 경로에 저장 (30일 넘는 장기 보관용, 최근 12주 유지)
- **수동**: 설정 화면에서 "내 평가 CSV"(엑셀용), "전체 JSON"(관리자, 복원용) 다운로드
- 사진은 R2에 이미 있으므로 별도 복사하지 않음

## 9. 위험 요소와 대응

| 위험 | 대응 |
| --- | --- |
| 쇼핑몰 구조 변경·차단으로 URL 추출 실패 | URL 추출은 "되면 좋은" 보조 기능으로만 설계, 실패 시 직접 입력으로 매끄럽게 전환 |
| 네이버 API 정책 변경 | 자동 입력 결과를 우리 DB에 저장하므로 기존 데이터는 영향 없음 |
| 쇼핑몰 이미지 링크 깨짐 | 기본 일러스트로 대체, "내 사진으로 바꾸기" 버튼 |
| 계정 R2 무료 10GB 초과 (다른 프로젝트 캐시 증가) | sf6-repository-opennext-cache 버킷에 수명 주기 규칙 추가 권장. 초과해도 GB-월당 $0.015 |
| D1 쓰기 요금 상한 없음 | 반복 쓰기 버그 방지 테스트, 월 1회 사용량 확인 |
| 맛 항목 기준이 사람마다 다름 | 항목별 짧은 기준 설명(예: 매운맛 3 = 신라면 정도) 표시 |
